# Архитектура

*English version: [../en/architecture.md](../en/architecture.md)*

## Зачем

У каждого репозитория свои скиллы, правила и знание собственной архитектуры. Задачу
качественнее и дешевле выполнит агент **внутри** целевого репозитория, чем агент-инициатор,
который лезет в чужой код со стороны. Нужен транспорт между репозиториями — и носителем
состояния выступает сам GitHub: задачи, комментарии, реакции. Ни внешнего сервиса,
ни общей базы, ни фоновых процессов.

## Поток

```
Репозиторий A (оркестратор)                    Репозиторий B (исполнитель)
──────────────────────────                     ───────────────────────────
изменения зафиксированы в ветке
  (git status чист — иначе спрашиваем человека)
  │
/handoff:dispatch
  │
  ├─ задача-родитель  #42 ◀── может быть заведена человеком заранее
  │    ├─ 📦 коммент-результат   ← ЕДИНСТВЕННЫЙ носитель контекста
  │    └─ 🔀 коммент-задача      ← таблица «репозиторий → статус → вопрос»
  │
  └─ создаёт ────────────────────────────────▶ задача-депендент #17
                                                 лейбл: agent-task
                                                 в теле: ссылка на контекст,
                                                         ссылка на коммент-задачу,
                                                         meta (chain, path, protocol)
                                                          │
                                               /handoff:inbox → /handoff:take
                                                          │  реакция 👀
                                                          │  ветка + работа + PR (Closes #17)
                                            ┌─────────────┴─────────────┐
                                       выполнил                    нужен человек
                                            │                           │
                                   /handoff:report              /handoff:block
                                  🚀 + задача ЗАКРЫТА            😕 коммент-вопрос
                                            │                           │
       /handoff:check ◀── строки таблицы обновляют исполнители          │
            │                                                          │
            │                            /handoff:answer ──────────────┘
            │                       ответ дописывается в тот же комментарий,
            │                       на нём появляется 👍, статус → NEW
            ▼
       /handoff:accept ──▶ нет блокировок и все депенденты закрыты → закрыть задачу-родителя
```

## Сущности

| Сущность | Где | Кто пишет | Как найти |
|---|---|---|---|
| задача-родитель | репозиторий-инициатор | только оркестратор | лейбл `handoff:parent` |
| коммент-результат | комментарий в задаче-родителе | автор результата, append-only | маркер `<!-- handoff:result -->` |
| коммент-задача | ровно один комментарий в задаче-родителе | владелец строки | маркер `<!-- handoff:routing -->` |
| коммент-вопрос | комментарий в задаче-депенденте | вопрос — исполнитель, ответ — в него же | маркер `<!-- handoff:question -->` |
| задача-депендент | целевой репозиторий | тело — оркестратор, комментарии — исполнитель | лейбл `agent-task` |

## Четыре правила целостности

1. **Статус — это реакция на задаче.** Плюс состояние open/closed. Таблица в коммент-задаче —
   кэш; её всегда можно пересобрать (`hf routing-render`), поэтому неудачная запись в таблицу
   не теряет состояние системы. Это главный приём против гонок.
2. **Выполненная задача — это закрытая задача.** Исполнитель закрывает её сам.
   Оркестратор не оценивает качество: закрыл — значит сделано.
3. **Владение строкой.** Строку `owner/repo` меняет только агент этого репозитория.
4. **Append-only, где возможно.** Результаты — новые комментарии. Единственная правка
   существующего комментария — ответ в коммент-вопрос, и он защищён оптимистической блокировкой.

## Отсутствие взаимных блокировок

- Нет синхронных ожиданий: ни одна команда не ждёт другой репозиторий.
- Циклы запрещены: в задаче есть путь `path: owner/a>owner/b`, повторное появление
  репозитория в пути отклоняется (код 4). Информация от предка запрашивается
  блокировкой с вопросом, а не встречной задачей.
- Глубина ограничена `HANDOFF_MAX_DEPTH`.
- Застрявшие задачи подсвечиваются в `/handoff:check`, но автоматических действий нет.
- Любая неопределённость заканчивается статусом BLOCKED и вопросом человеку.
  В том числе противоречие «👍 стоит, ответа нет» (код 7).

## Экономия токенов

| Приём | Где |
|---|---|
| детерминированная логика в bash, а не в промптах | `scripts/lib/*` |
| компактный вывод TSV вместо JSON-дампов | все подкоманды `hf` |
| один запрос GraphQL на весь список входящих со статусами | `hf inbox` |
| один запрос на задачу вместо трёх (статус + PR + даты) | `hf_issue_facts` |
| тонкие SKILL.md + справочники по ссылкам | `skills/handoff-protocol/references/` |
| жёсткие лимиты длины в шаблонах | `templates/` |
| запрет пересказа контекста: только ссылка на коммент-результат | `templates/task-body.md` |
| субагенты при `init` не ходят по ссылкам из README/AGENTS/CLAUDE | `skills/handoff-setup` |

## Кроссплатформенность

Поддерживаются Windows (Git Bash), Linux и macOS. Используются только POSIX-утилиты;
различия GNU/BSD закрыты фолбэками (`date`, `sha1sum`/`shasum`), `jq` не требуется,
`gh` ищется вне PATH по типичным путям установки.

## Границы

- Триггеров нет: исполнитель узнаёт о задаче из `/handoff:inbox` или из уведомления
  GitHub. Отсюда «полуавтоматическая» передача.
- Одна задача на пару «цепочка + репозиторий». Нужна вторая задача тому же
  репозиторию — заводится новая задача-родитель, то есть новая цепочка.
- Плагин не меняет код в чужих репозиториях и не делает коммитов за разработчика:
  при незафиксированных изменениях `dispatch` останавливается и спрашивает человека.
