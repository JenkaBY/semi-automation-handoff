# Установка и подготовка репозитория

*English version: [../en/setup.md](../en/setup.md)*

## 1. Требования к GitHub-токену

Один токен обслуживает **все** репозитории-участники — и свой, и соседние.
Плагин не только заводит задачи, но и работает с кодом: создаёт ветки, пушит их
и открывает pull request, — поэтому прав на одни issues недостаточно.

### Вариант А — fine-grained PAT (рекомендуется)

*Settings → Developer settings → Personal access tokens → Fine-grained tokens.*

**Repository access:** «Only select repositories» и перечислить **все**
репозитории-участники. «Only current repository» не подойдёт: плагин пишет в соседние.

| Разрешение        | Уровень      | Зачем                                                                    |
|-------------------|--------------|--------------------------------------------------------------------------|
| **Issues**        | Read & Write | задачи, комментарии, лейблы, реакции, закрытие                           |
| **Contents**      | Read & Write | чтение `README.md`/`AGENTS.md`/`CLAUDE.md` соседей, создание веток, push |
| **Pull requests** | Read & Write | создание PR и его привязка к задаче через секцию Development             |
| **Metadata**      | Read         | обязательно при любом другом разрешении                                  |

Больше ничего включать не нужно.

### Вариант Б — classic PAT

| Набор репозиториев          | Scope         |
|-----------------------------|---------------|
| есть хотя бы один приватный | `repo`        |
| все публичные               | `public_repo` |

### Дополнительные условия

- **Права учётной записи в репозитории.** Токен даёт возможность, но не полномочия.
  Чтобы закрывать задачи и пушить ветки, учётной записи нужен доступ не ниже **Write**
  (для работы только с задачами хватит **Triage**).
- **Организации с SAML SSO.** Токен нужно авторизовать в организации, иначе `gh`
  вернёт 403 `Resource protected by organization SAML enforcement`.
- **Issues должны быть включены** в каждом целевом репозитории:
  *Settings → General → Features → Issues*.
- **Лимиты API:** 5000 запросов в час. Типичный `/handoff:dispatch` на три репозитория —
  около 20 запросов, `/handoff:inbox` — один (GraphQL), `/handoff:check` — около пяти.
  При остатке меньше 200 `hf` предупредит.
- **Источник токена.** `GH_TOKEN` и `GITHUB_TOKEN` имеют приоритет над `gh auth login`.
  `hf doctor` печатает используемый источник — это первое, что стоит проверить,
  если «права вроде есть, а 403».

### Проверка

```bash
gh auth status
hf doctor
```

`gh auth status` показывает scopes только для classic-токенов. Для fine-grained
`hf doctor` проверяет права фактически: обращается к каждому соседу и различает
403 (нет прав) и 404 (нет доступа к репозиторию).

## 2. Предусловия рабочей станции

| Требование        | Проверка         | Примечание                                    |
|-------------------|------------------|-----------------------------------------------|
| `gh` версии 2.40+ | `gh --version`   | https://cli.github.com                        |
| авторизация `gh`  | `gh auth status` | `gh auth login`                               |
| bash              | `bash --version` | Windows — Git Bash; Linux и macOS — системный |
| git               | `git --version`  | нужен для определения корня репозитория       |

Поддерживаются **Windows (Git Bash), Linux и macOS**. Плагин использует только POSIX-утилиты,
а различия GNU/BSD (например, разбор дат в `date`) закрыты фолбэками. `jq` не нужен:
JSON разбирает встроенный в `gh` `--jq`, а локальная конфигурация — плоский `KEY=VALUE`.

Если `gh` установлен, но не виден в PATH (частый случай на Windows), плагин найдёт его сам
в типичных местах установки. Нестандартный путь задаётся переменной `HANDOFF_GH`:

```bash
export HANDOFF_GH="/c/Tools/gh/bin/gh.exe"      # Windows (Git Bash)
export HANDOFF_GH="/opt/gh/bin/gh"              # Linux / macOS
```

## 3. Подключение плагина

### Из GitHub (обычный случай)

В каждом репозитории-участнике:

```bash
/plugin marketplace add jenkaBY/semi-automation-handoff@v1.0.0
/plugin install handoff@handoff-marketplace
```

**Тег должен быть одинаковым во всех репозиториях** — это и есть гарантия совпадения версий.

### Из локальной копии (разработка плагина и работа без доступа к GitHub)

Marketplace можно подключить прямо из каталога на диске — указывается путь к корню
репозитория плагина, где лежит `.claude-plugin/marketplace.json`:

```bash
/plugin marketplace add /d/Workspace/semi-automation-handoff     # абсолютный путь
/plugin marketplace add ../semi-automation-handoff               # относительный
/plugin install handoff@handoff-marketplace
```

Обновление после правок в локальной копии:

```bash
/plugin marketplace update handoff-marketplace
```

То же самое в `.claude/settings.json` репозитория-участника:

```json
{
  "extraKnownMarketplaces": {
    "handoff-marketplace": {
      "source": {
        "source": "directory",
        "path": "/d/Workspace/semi-automation-handoff"
      }
    }
  },
  "enabledPlugins": {
    "handoff@handoff-marketplace": true
  }
}
```

Путь в `source: directory` разрешается относительно основного чекаута репозитория:
при запуске Claude Code из git worktree он всё равно указывает на основной чекаут.

Локальный путь — вариант для одной машины: у коллег он не разрешится. В общий репозиторий
коммитьте вариант с GitHub:

```json
{
  "extraKnownMarketplaces": {
    "handoff-marketplace": {
      "source": {
        "source": "github",
        "repo": "jenkaBY/semi-automation-handoff"
      }
    }
  },
  "enabledPlugins": {
    "handoff@handoff-marketplace": true
  }
}
```

Этот файл создаёт `/handoff:init`. Если `settings.json` уже есть, команда напечатает
фрагмент для ручного слияния и не тронет существующие настройки.

## 4. Подготовка репозитория

```
/handoff:init owner/web owner/infra
```

Команда выполняет по порядку:

1. `hf doctor` — предусловия. Красный пункт останавливает подготовку.
2. Опрос соседей субагентами: читаются `README.md`, `AGENTS.md`, `CLAUDE.md`
   и `.handoff/config.env`, **без переходов по ссылкам** из этих файлов (экономия токенов).
   Не более трёх субагентов параллельно, только чтение.
3. Сборку `.handoff/external-repos.md` — карты соседей, по 12 строк на репозиторий.
4. Предупреждение, если у соседа плагин не установлен или версия протокола расходится.
5. `hf config-init` — запись `.handoff/config.env`, добавление `.handoff/state.env`
   в `.gitignore`, создание `.claude/settings.json`.
6. `hf labels-ensure` — создание лейблов.
7. Повторный `hf doctor`.

### Что появляется в репозитории

| Файл                         | Коммитится | Назначение                                 |
|------------------------------|------------|--------------------------------------------|
| `.claude/settings.json`      | да         | автоподключение marketplace и плагина      |
| `.handoff/config.env`        | да         | список соседей, лимиты, имена лейблов      |
| `.handoff/external-repos.md` | да         | карта соседей для агента                   |
| `.handoff/peers.lock`        | да         | отпечатки источников карты: по ним обновление понимает, что изменилось |
| `.handoff/state.env`         | **нет**    | текущая задача сессии, локальное состояние |

### Лейблы

Всего два, и оба не про статус:

| Лейбл            | Зачем                                            |
|------------------|--------------------------------------------------|
| `agent-task`     | по нему `/handoff:inbox` находит входящие задачи |
| `handoff:parent` | по нему `/handoff:check` находит задачи-родители |

Статусы лейблами **не** обозначаются — для них используются реакции (👀 WIP, 😕 BLOCKED, 🚀 DONE, 👎 CANCELLED). `gh` не
умеет фильтровать по реакциям,
поэтому два лейбла остаются: они нужны ровно для фильтрации и больше ни для чего.

## 5. Готовность

Подготовка завершена, когда:

- `hf doctor` зелёный **в каждом** репозитории-участнике;
- версии плагина совпадают (`hf version`);
- пробный `/handoff:dispatch` из репозитория A создаёт задачу в репозитории B,
  и она видна там через `/handoff:inbox`.

## 6. Поддержание карты в актуальном состоянии

Соседние репозитории развиваются: назначение, стек и структура расходятся с тем, что
записано в `.handoff/external-repos.md`, а устаревшая карта заставляет оркестратора
делегировать не туда.

```
/handoff:refresh            # обновить то, что изменилось
/handoff:refresh --check    # только показать, что устарело, ничего не менять
```

Обновление дёшево, потому что сначала выясняет, что вообще изменилось: `hf peers-check`
одним GraphQL-запросом на репозиторий забирает только идентификаторы блобов
`README.md`, `AGENTS.md`, `CLAUDE.md` и `.handoff/config.env` — без их содержимого —
и сравнивает с `.handoff/peers.lock`. Субагенты тратятся только на репозитории со
статусом `stale` или `new`; `fresh` пропускаются полностью.

`hf doctor` показывает возраст карты по lock-файлу без единого сетевого запроса
и предупреждает, когда он превысил `HANDOFF_MAP_MAX_AGE_DAYS` (по умолчанию 30), —
напоминание приходит само. Обновиться стоит и сразу после крупного релиза у соседа.

`peers-check` заодно служит проверкой здоровья: он сообщает о соседе, где плагин
не установлен, и о том, у кого версия протокола разошлась с вашей.
