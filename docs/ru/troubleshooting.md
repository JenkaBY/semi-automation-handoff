# Диагностика проблем

*English version: [../en/troubleshooting.md](../en/troubleshooting.md)*

Первое действие при любой проблеме:

```bash
hf doctor
```

## Коды выхода `hf`

| Код | Значение | Что делать |
|---|---|---|
| 0 | успех | — |
| 2 | ошибка конфигурации, аргументов или условие не выполнено | исправить вызов; при «не в HANDOFF_PEERS» — `/handoff:init` |
| 3 | не выполнено предусловие | установить/авторизовать `gh`, создать лейблы |
| 4 | цикл или превышение глубины | не делегировать; задать вопрос через BLOCKED |
| 5 | несовпадение версии протокола | привести версии плагина к одной во всех репозиториях |
| 6 | сущность не найдена | проверить ссылку на задачу |
| 7 | 👍 на вопросе есть, ответа нет | остановиться, попросить человека дописать ответ |
| 75 | конфликт не разрешён за три попытки | BLOCKED + `hf routing-render` |

## Частые ситуации

### `gh: command not found`, хотя GitHub CLI установлен

Типично для Windows: `gh` есть, но PATH Git Bash о нём не знает. Плагин ищет его сам
в стандартных местах (Program Files, LOCALAPPDATA, `/usr/local/bin`, `/usr/bin`,
Homebrew на macOS и Linux). Нестандартный путь:

```bash
export HANDOFF_GH="/c/Tools/gh/bin/gh.exe"
```

### 403 при обращении к соседнему репозиторию

Варианты по убыванию частоты:

1. Fine-grained токен не включает этот репозиторий в Repository access.
2. Не хватает разрешения: нужны Issues — Read & Write, Contents — Read & Write,
   Pull requests — Read & Write.
3. Организация с SAML SSO — токен не авторизован для неё.
4. В окружении лежит `GH_TOKEN`/`GITHUB_TOKEN` от другой учётной записи и перекрывает
   `gh auth login`. `hf doctor` печатает используемый источник токена.

### 404 при обращении к соседнему репозиторию

Репозитория нет в доступе токена. Для приватных репозиториев 404 — обычный ответ
GitHub на «нет доступа», а не «не существует».

### Не закрывается задача или не пушится ветка

Учётной записи не хватает уровня доступа в целевом репозитории: для работы с кодом
нужен **Write**, для работы только с задачами — **Triage**. Прав токена самих по себе
недостаточно.

### Таблица статусов разошлась с реальностью

Источник истины — реакции на задачах-депендентах и их состояние open/closed. Восстановление:

```bash
hf routing-render --ref owner/api#42
hf check --ref owner/api#42
```

### Код 75 при записи статуса

Несколько агентов одновременно правят одну коммент-задачу. Статус на задаче уже выставлен,
состояние не потеряно. Действия: пометить задачу BLOCKED, сообщить человеку, затем
`hf routing-render`. Повторять запись «на удачу» не нужно — лимит попыток исчерпан осознанно.

### Код 7: 👍 стоит, а ответа нет

Кто-то отметил вопрос как отвеченный, но текст ответа в комментарий не дописал.
Работу возобновлять нельзя: попросите человека дописать ответ в **тот же** комментарий.
Отдельный комментарий с ответом протоколом не предусмотрен и найден не будет.

### Задача не появляется во входящих

1. `hf inbox --all` — возможно, она уже закрыта (то есть выполнена).
2. Есть ли лейбл `agent-task` (его ставит `hf task-create`).
3. Совпадает ли `HANDOFF_LABEL_TASK` в `.handoff/config.env` обоих репозиториев.

### `⚠no-PR` в сводке

Задача закрыта, но к ней не привязан pull request. Либо изменений в коде не было,
либо в описании PR забыли `Closes #<номер>` — без этого ключевого слова GitHub
не показывает PR в секции Development.

### Дубликаты задач

Не должны появляться: действует правило «одна задача на пару цепочка + репозиторий»,
повторный `task-create` возвращает `reused`. Если дубликат всё же есть — значит, задачи
из разных цепочек. Лишнюю пометьте CANCELLED и закройте.

### Версии плагина разошлись

```bash
hf version    # в каждом репозитории
```

Приведите все репозитории к одному тегу marketplace:

```
/plugin marketplace add jenkaBY/semi-automation-handoff@v0.2.0
```

## Проверка без сети

Слияние таблицы, оптимистическая блокировка, статусы-реакции, протокол «вопрос и ответ
в одном комментарии», защита от циклов и идемпотентность покрыты офлайн-тестами
на моках `gh`:

```bash
bash plugins/handoff/tests/run.sh
```
